# 01 · 设计理解与系统拆解

> **文档性质：** 对原始设计交接文档（V1.0）的理解、推断与结构化拆解。
> **前提：** 原始文档在 §5.2「重力房」处截断。本文只基于已收到内容做理解；缺失内容按用户要求由 AI 补全，统一标注在 `02-补全设计与待确认清单.md`，本文不把补全内容当作既定设计。

## 0. 先给结论：一句话 + 三个位移

**一句话理解：**

> 《折叠地牢》把「地牢」从一次性生成的探索容器，变成玩家可以拼装、布线、调参的战术装置；玩家收集的不是更强的装备，而是「房间规则」以及规则之间的组合方式。

可以用一个更技术性的类比来锁定它：

| 卡组构筑类 Roguelike | 《折叠地牢》的对应物 |
|---|---|
| 卡牌（效果组件） | 房间（规则组件） |
| 手牌 / 牌库 | 已获得的房间蓝图池 |
| 牌桌 / 出牌顺序 | 5×5 空间网格 + 房间摆放顺序 |
| 卡牌连携（combo） | 邻接传导 + 元素/能量反应 |
| 战斗中的出牌 | 房间内部的回合制战术战斗 |
| 局内构筑（拿牌/删牌） | 构筑节点上的放置 / 旋转 / 替换 |

这个类比能直接支撑开发：**它是一个「带空间牌桌的 Roguelike 构筑游戏」，而不是「带战斗的模拟经营」**。设计文档 §2.1 专门强调「不是城市建设游戏、不是自由建造沙盒」，正是为了避免后者。

从原始文档可以提炼出三个关键设计位移，它们是整个项目的技术需求来源：

1. **房间：地图内容 → 规则组件。**
   房间不是一张张地图，而是「可放置的规则单元」，必须能用数据描述（发射什么、传导什么、响应什么），否则做不出 12 种房间 × 组合。
2. **邻接：通行关系 → 效果传导网络。**
   门不只是「能不能走过去」，而是「热量/毒雾/能量/投射物能不能过去、以什么速率过去」。房间网格因此同时是一张**传播图**。
3. **战斗：数值对拼 → 利用自己搭建的规则地形。**
   同一场战斗换个布局结果应该不同；玩家赢输出，也赢在「把敌人推进毒雾房」这种空间决策上。

## 1. 五条设计理念 → 可验证的原型问题

理念只有在原型里能被证伪才有意义。以下把 §1.2 的五条原则翻译成开发时必须回答的问题：

| 原则 | 设计含义 | 原型阶段如何验证（验收问题） |
|---|---|---|
| 1. 空间本身就是构筑系统 | 换位置/换朝向会改变结果 | 同一组 4 个房间，摆成两种布局，同一场战斗的结果显著不同（不是数值随机，而是机制不同） |
| 2. 房间之间必须产生真实交互 | 效果能跨房间传播并改变状态 | 熔炉的热量进入毒雾房后能触发爆燃；这条因果链能在日志/UI 里被回溯 |
| 3. 玩家必须拥有主动规划能力 | 放置前能预判结果 | 构筑界面能预览「新房间放下后，哪些通道会连上、会触发什么反应」 |
| 4. 战斗必须与空间构筑深度结合 | 战斗策略依赖房间规则 | 敌人会被房间危害影响、也会被玩家利用；玩家可主动把战斗引导到有利房间 |
| 5. 随机性必须服务于策略 | 随机给机会，不给结论 | 随机只决定「拿到哪些房间、遇到什么敌人」；怎么摆、怎么打由玩家决定，且能提前看到足够信息 |

第 4 条是「回合制战术 + 空间构筑」最容易做假的地方：如果房间效果只是战斗开始时的数值 buff，就不算深度结合。本作的要求应是：房间规则在**战斗过程中持续改变战场**（地形、通道、投射物、单位状态），玩家和敌人都要对此做出反应。

## 2. 四层游戏循环

原文只写了单局流程（§3.1）和区域内容（§3.2），我将其补全为四层循环，便于后续系统和内容分层实现：

```text
【Meta 局外循环】
  解锁新房间/新规则/新初始能力 → 开启新一局
        │
        ▼
【Run 单局循环】（目标 30–45 分钟）
  选角色+初始房间 → 第 1 层 → …… → 第 N 层 → 地牢核心 → 胜负结算
        │
        ▼
【Floor 区域循环】
  起始房 → 普通/精英/事件/休整/商店房 → Boss 房 → 下一层
  （每层 8–12 个已构筑房间，玩家按资源与风险规划路径）
        │
        ▼
【Turn 回合循环】
  玩家行动 → 敌人行动 → 环境结算（排放→传导→反应→衰减）→ 状态检查
```

**理解要点：**

- **回合循环是规则系统的执行引擎。** 房间的「每两回合产生热浪」「每回合积累热量」等效果，都挂在回合钩子上；环境结算必须是一个**确定性的、可排序的管线**，否则组合效果会不可预测、不可测试。
- **房间既是地图又是棋盘。** 逻辑房间网格（5×5）与房间内部地面网格（9×9）是两层空间，二者的关系必须在技术上明确（见 §4.5）。
- **构筑发生在 Run 层，结算发生在 Turn 层。** 这是「规划」与「执行」的分离，也是本作节奏设计的支点：构筑阶段慢、可预判；战斗阶段快、有即时反馈。

### 2.1 体验样例：一局的前 20 分钟（用于校准理解）

> 以下基于 `02` 文档的补全假设，目的是让你快速判断「我理解到的体验」是否正确，不代表已定设计。

1. **开局（选择）**：选择初始角色「锻工」+ 起始房间「熔炉房」。熔炉房自带缓慢升温；你的地牢目前只有这一间房和两扇未连接的门。
2. **探索（第 1 个房间）**：从起始房穿过门，进入相邻的战斗房；用「移动 + 普攻」清掉 2 个史莱姆；获得蓝图「毒雾房」与 1 点构筑点。
3. **构筑（第一次决策）**：在构筑界面把毒雾房放在熔炉房南侧，旋转到门匹配。预览面板显示：*「热量将沿门传入毒雾房，预计第 3 回合达到爆燃条件」*——你第一次看到「空间 = 规则」。
4. **风险（第 2 个房间）**：毒雾房内敌人被毒伤，但玩家自己也会中毒。你必须在「站进毒雾利用它」和「在门外等爆燃」之间取舍——房间既是武器也是危险。
5. **组合（拿到镜面房）**：清房后获得镜面房蓝图。把它放在毒雾房东侧，旋转反射面朝向走廊；爆发时镜面把火焰冲击改道，烧到相邻房间的敌人——第一个「组合奖励」时刻。
6. **精英（利用布局）**：精英房的敌人会远程攻击。你用箭塔房/镜面反射把它逼进毒雾房，或者用风暴房把毒云吹进它的站位——战斗胜负由布局+操作共同决定。
7. **Boss（构筑成为解法）**：Boss 会把自己的热量推给你；你需要在 Boss 房隔壁建好毒雾房，并用「折叠房」把两个不相邻房间折在一起制造跨图爆燃，或用镜面把 Boss 的火焰攻击反射回去。
8. **结算**：通关本层 → 获得新蓝图/构筑点 → 进入下一层（更深的地牢、更复杂的规则组合）。

**这 8 步是后续「可玩性验收」的脚本原型**：M4 垂直切片必须至少能复现其中 1–7 步。

## 3. 系统拆解与优先级

按「对验证核心卖点的必要性」排序。P0 = 不做就无法验证游戏是否成立；P1 = 首个可玩版本必需；P2 = 后续再做。

| 系统 | 内容 | 优先级 | 首个原型验证的问题 |
|---|---|---|---|
| 空间构筑 | 5×5 逻辑网格、房间放置/旋转/替换、门匹配、连通性校验 | **P0** | 旋转与放置是否有真实后果、操作是否顺畅 |
| 规则引擎 | 环境通道（热/毒/冷/能量/风）、传导、阈值反应、房间钩子 | **P0** | 房间组合是否真的「涌现」，而非硬编码 |
| 回合调度 | 玩家/敌人/环境三段式回合、定时器、事件顺序 | **P0** | 规则结算是否可预测、可复现 |
| 战斗 | 网格移动、攻击、投射物、击退、地形危害、敌人 AI | **P0**（最小版） | 空间规则是否进入战斗决策 |
| 单局结构 | 房间节点类型、构筑节点、蓝图获取、路径选择 | P1 | 一局 30–45 分钟是否成立、是否「构筑 5 分钟打 1 分钟」 |
| 经济与资源 | 金币、构筑材料/构筑点、房间购买、修复 | P1 | 构筑是否有取舍（不是想建就建） |
| 事件/休整/商店 | 选择事件、临时重排、商店、休整 | P1 | 节奏与风险回报是否成立 |
| Boss | 利用空间规则的关底敌人 | P1 | 房间构筑能否成为 Boss 战的解法 |
| UI/信息呈现 | 构筑预览、规则说明、状态图标、效果动画 | **P0（最小版）** | 玩家能否看懂房间规则与传导 |
| 局外成长 | 解锁房间/规则/初始能力 | P2 | —（首个可玩版本不做） |
| 存档 | 局内断点、种子 | P2 | 可在垂直切片后再做 |
| 视听表现 | 像素/手绘方向、音效 | P2 | 原型先用色块占位 |

**范围结论：** 首个可运行原型应聚焦「构筑 + 规则引擎 + 最小战斗 + 可读性 UI」四件事。内容上先做 6 个房间（足以覆盖元素、转换、传输、战斗、特殊五类交互），引擎验证成立后再扩到 12 个。

## 4. 空间构筑系统：理解与拆解

### 4.1 两层空间模型

| 层 | 单位 | 作用 | 技术含义 |
|---|---|---|---|
| 宏观层 | 房间格（5×5） | 玩家构筑的布局；房间之间的邻接与传播 | 一张**房间图**（Room Graph），节点=房间，边=共享边+双门 |
| 微观层 | 地面格（房间内 9×9，见 §4.2） | 角色移动、战斗、局部地形与危害 | 每房间一张 TileMap/网格 |

两层的连接点：门。门既是宏观层的边，也是微观层的一个可通行格。**所有跨房间的效果（传导、投射物、单位移动）都必须经过门**——这是可读性和规则一致性的基础。

### 4.2 房间几何、门表示与旋转（P0-1 已冻结）

**房间内部网格统一为 9×9（正方形）。** 原文 §4.1 的「9×7」仅为示意，不是最终尺寸；9×7 无法在 90° 旋转后保持门位对齐，因此不采用。房间局部坐标跨度为 `[0,9]×[0,9]`，地面格 `(x,y)` 覆盖 `[x,x+1]×[y,y+1]`；最外圈为墙体，可走区域为 `1..7`。

- **门格（tile）**：基准朝向（orientation 0）下 N 门格 `(4,0)`、E 门格 `(8,4)`、S 门格 `(4,8)`、W 门格 `(0,4)`。
- **门锚点（墙边中点）**：N `(4.5,0)`、E `(9,4.5)`、S `(4.5,9)`、W `(0,4.5)`；**相邻两个房间的门锚点在世界坐标中严格重合**（共享边的中点），两个门格分别位于各自房间的外环墙上，跨门移动经过两格门洞。
- **旋转 90°** 围绕房间中心 `(4.5,4.5)` 进行：门格、门锚点、内部地形、规则方向性（镜面反射方向、重力方向、导管朝向、箭塔朝向）全部用同一变换处理；4 个朝向的 footprint 始终是 9×9，旋转后门锚点重合不变量仍成立。
- 房间用 4 位掩码表示门：`N=1, E=2, S=4, W=8`（基准朝向）。旋转 90° 时门掩码循环移位：`N→E→S→W→N`。
- **旋转作用于房间实例的朝向状态（orientation），而不是只对贴图做视觉变换**：实现上旋转的是房间数据层（门格/锚点/地形/规则方向），表现层再按同一朝向渲染（对应 02 文档 D4 方案 A）。

> 这项几何决定是 B1 的修复方案：门锚点对齐使「旋转后门位错 1 格」问题从根上消失，M0 会用单测覆盖 4 朝向 × 4 面墙的全组合。

### 4.3 放置校验（原文 §4.2 六条规则的工程化）

放置校验需要按顺序执行，且必须给出**可读的失败原因**（用于 UI 提示）：

1. 目标格在 5×5 范围内；
2. 目标格为空（替换另走替换流程）；
3. 若为空布局（第一步）：房间不要求邻接，但要求房间至少有一扇门朝向可拓展方向（或直接放起始房间）；
4. 非空布局：至少存在一个相邻房间，且「相邻房间朝向我方的门」与「我朝向它的门」**同时存在**（门对门，不允许单边门连接）；
5. 不能有门指向地图边界（门对墙不可通行）；
6. 放置后已建房间图仍**连通**（从起始房间可到达所有房间），且起始房 → Boss 房的必经路径不失效；
7. 满足构筑点数/房间数/特殊限制。

第 6 条需要一次图连通性检查（BFS/DFS），在 5×5 规模下成本可忽略。替换房间时同样要检查「移除后是否断连」，这是构筑系统里最容易出现 bug 的地方之一。

### 4.4 构筑时机（原文 §4.3 的约束）

原文限定：探索期只能在构筑节点操作、战斗期不能改、事件可临时重排、休整房可替换一个房间或旋转部分房间。理解其设计意图：

- **不让玩家无限试错**：构筑要有资源成本与时机成本，否则「空间」不再是决策，只是编辑器。
- **不让战斗变成暂停改地图**：战斗中的空间变化只能由**房间规则**产生（例如爆燃改变地形、蓄能房释放），而不是玩家手动重排。这样空间规则的「自动性」和玩家的「规划性」分野清晰。
- 由此推出实现要求：**构筑操作必须是独立的权力（authority）**，用状态机控制 `Exploring / Building / Combat / Rest` 等阶段，各阶段允许的操作集合不同。

### 4.5 「折叠」到底是什么？（原文最大的未定义项）

标题叫《折叠地牢》（Folded Dungeon），但正文没有定义「折叠」机制；正文只定义了放置、旋转、替换、邻接。这是一个**必须在进入开发前确认的设计缺口**。我列出三种可能，供设计者选择（详见 02 文档 D1）：

| 解释 | 含义 | 对设计的影响 |
|---|---|---|
| A. 隐喻：「折叠」= 玩家把房间拼折成地牢 | 标题是修辞，不新增机制 | 风险：名字承诺了独有机制却没兑现 |
| B. 操作：旋转/重排本身就是「折叠」 | 房间旋转 = 空间折叠的具象化 | 最省成本，但新意有限 |
| C. 机制：真正的空间折叠 | 例如花费「折叠点」把两个不相邻房间临时视为相邻、把房间对折使两扇门直连、或把远端敌人的位置折叠到玩家面前 | 若能实现，是招牌机制；但会同时增加规则复杂度与实现风险 |

**我的建议：** 采用 C 的轻量版（首个可玩版本至少实现「折叠房」+ 1 次/层的定向邻接改写），否则名称与玩法不匹配。**但这一点必须由设计者确认。**

## 5. 规则系统：从「三个层次」推导出统一模型

原文 §4.4 要求房间有三层作用（局部/邻接/组合），又明确要求「不能把所有房间组合都写成硬编码」。这是整个项目**技术上最核心的需求**。我的理解与推导如下。

### 5.1 统一抽象：通道 + 状态 + 反应配方 + 结算管线

把三层作用映射到一套可复用模型上：

| 原文层次 | 抽象 | 说明 |
|---|---|---|
| 局部效果 | **房间状态**（room state）+ **本地规则** | 房间自己每回合演化的变量（热量、毒雾浓度、蓄能量、计时器）与本地效果（热浪、伤害、加速/减速） |
| 邻接效果 | **通道传导**（channel propagation） | 环境变量沿「门对门」的房间边扩散/传导/衰减；不同通道有不同传导规则 |
| 组合效果 | **反应配方**（reaction recipe） | 「当某房间满足一组条件时，执行一组效果」的数据化规则；不是按房间对硬编码，而是按**条件+效果**组合 |

这样设计的好处：

- 新增房间 = 新增数据（发射/吸收/传导/反应能力），不需要改引擎代码；
- 组合数量随通道与配方的组合增长，而不是随「房间对」数量爆炸；
- 玩家能学到**规则本身**（热+毒=爆燃），从而在新房间里迁移理解——这正是「策略性」的来源。

### 5.2 通道草案

| 通道 | 语义 | 来源举例 | 被影响/消耗于 | 表现 |
|---|---|---|---|---|
| Heat 热量 | 温度积累 | 熔炉、爆燃 | 毒雾（爆燃）、冰霜（相消）、蓄能（转化为能量） | 红色热浪、屏幕暖色 |
| Toxin 毒雾 | 毒性气体 | 毒雾房 | 受热爆燃、被风吹动、被冻结 | 绿色雾、中毒图标 |
| Cold 寒冷 | 降温 | 冰霜房 | 抑制热/毒反应、冻结地形 | 蓝白霜冻 |
| Charge 能量 | 可储存/释放的能量 | 蓄能房、风暴房、镜面反射 | 释放为攻击/强化 | 电光、脉冲 |
| Airflow 气流 | 风向与风力 | 风暴房 | 推动毒雾/火焰/投射物 | 粒子方向 |

（`Fire 燃烧` 更适合作为**状态**而非通道：由 Heat 达标+可燃物触发的持续状态，会自己产生 Heat。状态与通道分开是避免「热产生热」正反馈失控的关键。）

**投射物/射束不是通道。** 镜面反射、风暴偏转、重力弯折处理的是「实体投射物路径事件」，与房间环境的标量通道是两套系统；两者通过反应配方（例如爆燃生成火焰冲击实体）交互。这样通道数量克制在 5 个，且投射物规则可被多个房间复用。

### 5.3 回合结算管线（确定性）

每回合环境结算按固定阶段执行，顺序必须稳定：

```text
1. 玩家阶段 / 敌人阶段（行动、攻击、移动、投射物飞行）
2. 环境阶段
   2.1 计时器与状态推进（燃烧、中毒、冻结的持续时间）
   2.2 本回合排放（emitters：熔炉 +heat、毒雾 +toxin……）
   2.3 状态效果伤害（站在毒雾里、被火覆盖）
   2.4 传导（按通道逐个扩散：沿房间图 BFS，门对门传导，按固定房间顺序）
   2.5 反应判定（reaction recipes，按优先级排序，检查条件并排队效果）
   2.6 反应效果执行（伤害、生成火/地形变化、传导方向改变、能量释放）
   2.7 衰减与清理（通道自然衰减、超阈值削顶、临时状态移除）
3. 状态检查（死亡、胜负、触发事件）
```

**确定性要求（工程硬约束）：**
- 遍历顺序固定（房间按 row-major 索引排序），不使用哈希表迭代顺序；
- 随机数全部来自**带种子的 RNG 实例**，禁止全局 `randi()`；
- 每个阶段产生的事件进入**事件日志**，供调试、回放与自动化测试使用。

### 5.4 示例：熔炉 + 毒雾 + 镜面 的完整结算链

用数值走一遍（数值仅为示意，用于验证机制链路）：

- 熔炉房：每回合 `heat += 0.25`（上限 1.0）；向门对门的相邻房间传导 `传导率 0.4`。
- 毒雾房：每回合 `toxin += 0.2`（上限 1.0）；**反应配方「爆燃」**：本房间 `heat ≥ 0.6` 且 `toxin ≥ 0.3` → 对房间内所有单位造成伤害、生成燃烧状态、heat 溢出 +0.3。
- 镜面房：带方向性的转换房；**反应配方「反射」**：当有「射束/火焰传播」事件试图穿过本房间的门时，把传播方向改为房间朝向决定的方向。

推演：

| 回合 | 熔炉 heat | 毒雾 heat | 毒雾 toxin | 事件 |
|---|---|---|---|---|
| 1 | 0.25 | 0.10 | 0.20 | 熔炉排放 +0.25；向毒雾传导 0.25×0.4 |
| 2 | 0.50 | 0.30 | 0.40 | 传导累积 |
| 3 | 0.75 | 0.60 | 0.60 | **爆燃触发**：heat 0.60≥0.6 且 toxin 0.60≥0.3 ✓ → 范围伤害；随后镜面房把火焰冲击改为侧向传播 → 命中相邻房间敌人 |

**传导公式（M2 已定稿）：** 每回合每个通道只结算一跳；对每条门对门边（含折叠虚拟边），只有高值房间向低值房间传；接收量 = `floor(源值 × 传导率 / 100)`；同阶段所有边用阶段开始快照同时计算。热/毒/冷/风是环境场（不扣源），能量 CHARGE 守恒（源按接收量扣除）。上表即按此公式推演（第 1/2/3 回合毒雾房热量 = 0.1/0.3/0.6，毒素 = 0.2/0.4/0.6 → 第 3 回合爆燃）。

这条链必须能被玩家在构筑界面预判（预览第 3 回合触发），并且战斗日志必须能解释「为什么这里爆燃了」。**可读性 = 规则可信度 = 策略存在感。**

### 5.5 必须规避的反模式

| 反模式 | 后果 | 规避方式 |
|---|---|---|
| 按房间对硬编码组合效果 | 12 房间需要 66 对，无法维护与扩展 | 通道 + 条件配方 |
| 隐藏规则、不可视传导 | 玩家觉得随机、不公平 | 状态图标、地面染色、传导箭头、日志 |
| 正反馈无上限（热生热、毒生毒） | 数值爆炸、战斗失控 | 通道削顶、衰减、状态与通道分离 |
| 传导穿墙（不走门） | 空间规则失去意义 | 只在「门对门」的边上传导 |
| 组合效果只加数值不变战场 | 违背原则 4 | 反应必须产生可见的战场变化（地形/位移/状态） |

## 6. 战斗系统：理解要点

原文只给到方向性描述（2D 俯视角、房间内网格移动、回合制、战术），没有系统规则。我理解其需求边界如下（详细提案见 02 文档 B3）：

1. **战场 = 房间内部网格（9×9）**，战斗以房间为单位发生；房间切换靠门。
2. **时间 = 回合制**：玩家行动 → 敌人行动 → 环境结算。环境结算与战斗共用同一个回合管线（这是「空间规则进入战斗」的技术前提）。
3. **移动与位移是战术核心**：因为毒雾、热浪、击退、重力、风都作用于「位置」，所以移动/击退/位移三者在同一套网格坐标系上结算。
4. **投射物是可被房间规则改写的一等公民**：镜面反射、风暴偏转、重力弯折、箭塔自动射击、导管传递——同一个投射物系统要被多个房间复用。
5. **敌人也必须受房间规则影响**，并且 AI 至少要能做「利用 / 规避」两类决策，否则房间规则只对玩家生效会显得虚假。
6. **首发版本不需要复杂小队系统**：先用「单个玩家角色 + 若干敌人类型」验证空间战术，再考虑扩展（D2）。

---

**M3 实现摘要（2026-10-30）：** 玩家阶段（移动 3 + 1 行动：普攻/等待）→ 敌人阶段（BFS 追击、相邻攻击、避开下一回合致命危害）→ 环境阶段（`RuleEngine.tick` → 箭塔投射物 → 房间危害伤害 → 状态 DoT/计时/新状态 → 胜负）。投射物为**房间级**抽象：沿门逐房间推进、镜面房转向、命中首个目标；多单位 initiative、逐格弹道、风暴/重力房改写留待后续（随内容一起补）。

## 7. 随机性与策略的边界

原文原则 5 要求「随机服务策略」。我的划分建议：

| 随机决定 | 玩家决定 |
|---|---|
| 房间蓝图池（抽到哪些房间） | 拿哪个、摆哪里、怎么转 |
| 敌人配置/精英词缀 | 走哪条路径、在哪个房间接战 |
| 事件选项与商店库存 | 资源分配（买房间/买强化/留钱） |
| Boss 类型 | 构筑应对与战斗执行 |

关键工程要求：**信息提前量**。构筑前能看到新房间的规则说明与预计传导/反应预览；战斗前能看到房间当前状态（下回合是否会爆燃）；这样「随机」才不会变成「听天由命」。

## 8. 主要设计风险

| # | 风险 | 影响 | 缓解建议 |
|---|---|---|---|
| R1 | 组合爆炸导致平衡与验证成本失控 | 高 | 通道数量克制（首版 5 个）；配方用统一条件/效果；自动化组合测试覆盖 |
| R2 | 规则不可读，玩家看不懂为何受伤 | 高 | 构筑预览 + 状态 HUD + 传导可视化 + 战斗日志；「规则解释」作为 UI 一等功能 |
| R3 | 构筑与战斗节奏割裂（造 5 分钟打 1 分钟） | 中高 | 构筑在短节点内完成；战斗短而密集；让房间效果在战斗内持续产生变化 |
| R4 | 构筑自由度与关卡目标冲突（强制路径/必经点） | 中 | 用「连通性 + Boss 房接入」做最小约束；预留「出口房/上传点」概念 |
| R5 | 2D 像素表现力不足以表达空间规则 | 中 | 原型用色块+线框+粒子先验证；后期再定美术；表现层与模拟层分离 |
| R6 | 单局时长 30–45 分钟与内容量不匹配 | 中 | 首个切片控制 15–20 分钟，验证节奏后再加内容 |
| R7 | 确定性/存档复杂度被低估（回放、种子、断点） | 中 | 模拟层纯数据 + 种子 RNG + 事件日志，从第一天就做 |
| R8 | 「折叠」机制若缺失，标题与玩法不匹配 | 中高 | 尽早确认 D1，必要时用轻量版折叠房实现 |
