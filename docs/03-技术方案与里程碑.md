## 2. 核心架构原则

### 原则 1：模拟层与表现层分离（最重要）

```text
┌──────────────────────────────────────────────┐
│ 表现层 presentation/（Node2D、Control、动画）│
│   订阅 sim 事件 → 更新视图；不写规则逻辑      │
└───────────────▲──────────────────────────────┘
                │ 事件（EventBus，RefCounted 信号）
┌───────────────┴──────────────────────────────┐
│ 模拟层 core/（纯 GDScript 类，无场景依赖）   │
│   网格 / 房间实例 / 通道 / 规则 / 回合 / 战斗 │
│   可无头运行，100% 可单测                    │
└──────────────────────────────────────────────┘
```

- 模拟层不依赖任何节点、场景、渲染；所有状态是普通对象；
- 表现层只读状态、播放动画、转发输入；**绝不在视图里改规则数值**；
- 好处：规则可单测、可回放、可批量模拟组合效果（平衡性救星）、将来可换表现层。

### 原则 2：数据驱动

房间、反应配方、敌人、效果全部是 Resource 数据；新增内容不改引擎代码。

### 原则 3：确定性

- 房间遍历、效果结算顺序固定（row-major + 优先级）；
- 唯一随机源 = 带种子 RNG（每局一个种子）；
- 每个阶段产生结构化事件日志（调试、回放、测试断言都用它）。

### 原则 4：事件日志驱动反馈

所有规则结算产生事件（`channel_changed`、`reaction_triggered`、`damage_dealt`、`projectile_reflected`……），用于：
- 表现层动画/特效/战斗日志；
- 自动化测试断言；
- 规则解释 UI（「为什么这里爆燃」）。

## 4. 核心数据模型

### 4.1 RoomDef（房间定义，Resource）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | StringName | 唯一 ID，如 `&"forge"` |
| `display_name` | String | 「熔炉房」 |
| `category` | int（枚举） | 元素/转换/传输/战斗/资源/特殊 |
| `door_mask` | int | 4 位：N=1 E=2 S=4 W=8（基准朝向） |
| `layout` | RoomLayout | 内部布局的**纯数据**引用（尺寸/地形/门格/出生点/危害格）；不引用场景 |
| `emitters` | Array[ChannelEmitter] | 每回合排放的通道与速率/上限 |
| `absorbers` | Array[ChannelAbsorber] | 吸收相邻通道（蓄能房） |
| `transfer_rate` | float | 本房间作为传导中介的倍率（导管房 1.5） |
| `local_effects` | Array[EffectDef] | 本地效果（热浪、毒伤、减速） |
| `tags` | Array[StringName] | `flammable`、`gas_source`、`heat_source`、`mirror`…… 供配方条件匹配 |
| `build_cost` | int | 构筑点消耗 |
| `description` | String | 规则文案（UI 用，自动生成+人工润色） |

#### RoomLayout（纯数据 Resource，B3 修复）

| 字段 | 类型 | 说明 |
|---|---|---|
| `size` | Vector2i | 恒为 `(9, 9)`（P0-1；加载校验强制） |
| `terrain` | PackedInt32Array | 9×9 地形/障碍编码（0=可走，1=墙，其它值留给地形类型） |
| `door_cells` | Dictionary | 方向(int) → 房间外环门格 `Vector2i`；由门锚点派生，加载时校验 |
| `door_anchors` | Dictionary | 方向(int) → 墙边中点局部坐标（N `(4.5,0)`…） |
| `spawn_cells` | Array[Vector2i] | 出生点候选（可走区内） |
| `hazard_cells` | Dictionary | 通道类型 → 初始危害格数组（M2 起使用） |

**数据/表现分离（B3）：** `RoomDef` 与 `RoomLayout` 不出现 `PackedScene`/`Node`/`View` 字段；表现层用 `layout_id → 场景/渲染器` 的映射表实现，模拟层只读纯数据。同一 `.tres` 被多个房间实例共享时，运行时状态一律放 `RoomInstance`（或独立状态对象）。

### 4.2 通道（Channel）

固定枚举 + 索引数组存储，保证遍历顺序确定：

```gdscript
enum Channel { HEAT, TOXIN, COLD, CHARGE, AIRFLOW }   # 首版 5 通道（投射物/射束是独立实体系统，不进通道）
# 每房间状态：PackedInt32Array（定点整数 0..1000），长度 = Channel.size()（=5），下标即通道枚举
# 阈值也用定点整数表示：Heat 600 = 60%，Toxin 300 = 30%（禁止用 float 阈值比较）
```

全局参数（`data/balance/channels.tres`）：每通道 `max_value=1000`、`decay_per_turn`（整数）、`default_transfer_rate`（整数百分比）、`threshold`（定点整数）。

### 4.3 ReactionRecipe（反应配方，Resource）

| 字段 | 说明 |
|---|---|
| `id` / `priority` | 唯一 ID；优先级决定同帧结算顺序 |
| `where` | `SAME_ROOM` / `NEIGHBOR_ROOM` / `EDGE`（跨门事件） |
| `conditions` | 条件数组（AND）：`ChannelAtLeast`、`ChannelAtMost`、`HasTag`、`HasState`、`TriggeredByEvent` |
| `effects` | 效果数组：`DamageArea`、`AddChannel`、`SetState`、`SpawnFire`、`RedirectPropagation`、`ReleaseCharge`、`ChangeTerrain` |
| `cooldown_turns` | 防刷屏/防自循环 |
| `event_id` | 触发事件类型（如「爆燃」用于 UI 与日志） |

**关键点：配方条件基于「通道 + 标签 + 事件」，而不是硬编码房间 ID。** 例如爆燃配方只需要「可燃气体标签 + Heat≥阈值 + Toxin≥阈值」，任何未来房间只要带 `gas_source`/`flammable` 标签就能触发。这是「可复用的规则系统」的落地方式。

### 4.4 EffectDef（效果，Resource 子类）

| 效果 | 用途 |
|---|---|
| `DamageArea` | 对房间内区域/单位造成伤害（爆燃、热浪） |
| `AddChannel` | 修改通道数值（排放、中和、溢出） |
| `SetUnitState` | 燃烧/中毒/寒冷/充能/眩晕 |
| `SpawnProjectile` | 箭塔、镜面反射、爆燃火焰冲击 |
| `RedirectPropagation` | 镜面/重力改写传播方向 |
| `ReleaseCharge` | 蓄能房释放 |
| `ChangeTerrain` | 冻结毒雾/点燃地面（后续） |

## 5. 核心算法

### 5.1 房间放置与旋转（M0）

**几何（P0-1 冻结）：** 房间 9×9；基准朝向下门格 N`(4,0)` E`(8,4)` S`(4,8)` W`(0,4)`，门锚点（墙边中点）N`(4.5,0)` E`(9,4.5)` S`(4.5,9)` W`(0,4.5)`；相邻房间门锚点世界坐标必须严格相等。

```text
rotate_mask(mask, steps):          # steps ∈ {0,1,2,3}，顺时针 90°，N→E→S→W
rotate_cell(cell, steps):          # 绕房间中心 (4.5,4.5) 旋转，返回朝向 steps 下的本地格
rotate_anchor(anchor, steps):      # 同一旋转变换
door_anchor_world(instance, dir):  # cell_origin(instance.cell) + rotate_anchor(local_anchor(dir), orientation)

# 放置：先构造 tentative layout，全部通过才提交（失败不改真实状态）
can_place(def, orientation, cell) -> Result(ok, reason_code, detail):
 1. cell ∈ 5×5                                -> CELL_OUT_OF_BOUNDS
 2. cell 为空                                  -> CELL_OCCUPIED
 3. 所有门不指向 5×5 外                        -> DOOR_TO_BOUNDARY
 4. 若已有已建房间：
    4.1 至少一个相邻房间                        -> NO_CONNECTION
    4.2 对每个相邻已建房：
        - 双方都在共享边有门  -> 记录一条边
        - 双方都无门          -> 无连接，允许
        - 已建房有门、新房无门 -> DOOR_SEALED（封死已有门）
        - 新房有门、已建房无门 -> DOOR_TO_WALL（门对墙）
 5. 临时加入后，已建房间图连通（从起始房 BFS）  -> DISCONNECTED
 6. 起始房 → Boss 房（若已放置）仍连通          -> REQUIRED_PATH_BROKEN
 7. 房间数上限 / 构筑点足够                     -> ROOM_LIMIT / NO_BUILD_RESOURCE
 注：门可以朝向地图内的空格（预留扩展），不算失败。

can_rotate(instance, new_orientation) -> Result:
 1. 房间存在                                   -> ROOM_NOT_FOUND
 2. 旋转后与所有相邻房间的门仍成对（不得封门）   -> ROTATION_BREAKS_CONNECTION
 3. 旋转后已建房间图仍连通                      -> DISCONNECTED
 4. 旋转后起始房 → Boss 仍连通                  -> REQUIRED_PATH_BROKEN

can_replace(instance, new_def, new_orientation) -> Result:
 1. 以「移除旧房 + 放置新房」构造 tentative      -> 复用 can_place 的全部失败码
 2. 替换后已建房间图仍连通                      -> DISCONNECTED
 3. 替换后起始房 → Boss 仍连通                  -> REQUIRED_PATH_BROKEN
 4. 资源：新 cost + 旧房返还 floor(old_cost/2)   -> NO_BUILD_RESOURCE
```

**不变量（M0 单测必须逐条覆盖）：** 空盘首放不要求邻接（起始房直接放）；非空盘放置必须有至少一条门对门的边；已有门不得被封死；不得把门对到邻房墙上；不得把门指向地图边界；任何 mutation 后已建图连通、起始房→Boss 路径不失效；tentative 校验失败时真实状态不变；替换必须按规则结算资源。

### 5.2 通道传导（M2）

- 遍历通道优先级（Heat → Toxin → Cold → Charge → Airflow），每个通道独立传导；
- 传导路径：房间图 BFS，仅沿「门对门」边（含折叠虚拟边）；
- 每个房间 `new = old + sum(neighbor_surplus × rate) - decay`，先算全量再统一写入（避免顺序依赖）；
- 传导量受 `max_value` 削顶；每个房间每回合最多接收一次（防环）；
- 产出传导事件（from、to、channel、amount）供可视化。

### 5.3 投射物路径（M3）

```text
trace_path(origin, direction, world):
    逐格推进，遇到：
      1. 墙/障碍 → 停止
      2. 门 → 进入相邻房间（方向保持）
      3. 镜面房背面 → 反射方向（按朝向）
      4. 风暴/重力 → 偏转/加速（每格检查）
      5. 单位 → 命中结算
    所有事件写入事件日志
```

用**同一套路径追踪**服务：玩家远程攻击、箭塔、爆燃火焰传播、镜面反射——保证规则一致、可测试。

### 5.4 回合调度（M2）

```text
TurnScheduler.begin_turn():
  phase = PLAYER     # 等待输入；探索态为自由移动
  phase = ENEMY      # AI 依次行动
  phase = ENVIRONMENT:
     1 状态计时器推进
     2 房间排放（emitters）
     3 状态伤害（毒/火）
     4 通道传导（5.2）
     5 反应判定（按 priority 排序、row-major 顺序）
     6 反应效果执行
     7 衰减/削顶/清理
  phase = CHECK      # 死亡/胜负/事件触发
  turn += 1
```

> 确定性测试：同一种子 + 同一输入序列 → 事件日志逐条一致（黄金回放测试）。

- **验收：** 完整可玩一层；构筑决策有可见后果；组合效果触发有明显反馈；无阻塞性 bug。

## 8. 风险与应对（技术侧）

| # | 技术风险 | 应对 |
|---|---|---|
| T1 | 浮点通道数值导致不确定性 | 状态量化（如 0.01 精度 / 定点整数 0–1000）；同种子黄金回放测试 |
| T2 | 组合效果产生无限循环（热生热、回声重复折叠） | 每回合每房间最多触发配方次数；通道削顶；事件类型白名单 |
| T3 | 旋转后房间内部布局破绽（门对不上、障碍堵门） | 房间内部布局规范：门位固定、旋转后自动生成；编辑器校验脚本 |
| T4 | 表现层与模拟层状态不同步 | 单向数据流：输入→Sim→事件→View；禁止 View 直接改 Sim |
| T5 | 房间数据与配方数据互相引用复杂 | RoomDef 只带标签/数值，配方独立注册；加载期校验引用完整性 |
| T6 | 无头测试运行器与场景加载冲突 | 测试只加载 core/ 纯类；场景相关测试单独标记需求 headless display |
| T7 | 内容验证成本（12 房间组合太多） | 组合自动化测试矩阵（标签组合而非房间对）；先 6 房间 |
